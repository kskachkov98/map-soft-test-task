# Medical Surveys Templates API

Read-only backend-приложение на FastAPI для отдачи шаблонов медицинских анкет со сложной иерархической структурой.

## 🚀 Быстрый запуск (Docker Compose)

Все компоненты приложения (FastAPI, PostgreSQL, автоматическое создание схемы и наполнение базы данными) поднимаются **одной командой**:

```bash
docker compose up --build
```

Перед выполнением может понадобиться выдать права на файлы compose/entrypoint и compose/start:

```bash
sudo chmod +rx compose/entrypoint
sudo chmod +rx compose/start
```

Самый быстрый способ развернуть и подготовить приложение одной командой (автоматически соберет образы, запустит контейнеры, создаст схему и зальет тестовые данные):

```bash
make setup
```

Если вы хотите управлять процессами в Docker пошагово, используйте следующие команды:

* **Сборка/пересборка Docker-образов:**
  ```bash
  make build
  ```
* **Запуск контейнеров (FastAPI + PostgreSQL) с выводом логов в терминал:**
  ```bash
  make run
  ```
* **Создание схемы таблиц внутри запущенного контейнера:**
  ```bash
  make db-init
  ```
* **Наполнение базы данных из JSON-файла внутри контейнера:**
  ```bash
  make db-seed
  ```

После успешного запуска:
* **API и Документация OpenAPI (Swagger UI):** [http://localhost:8000/docs](http://localhost:8000/docs)
* Альтернативная документация (ReDoc): [http://localhost:8000/redoc](http://localhost:8000/redoc)

## 💻 Локальный запуск без Docker (Local Host)

Для запуска на локальной хост-машине требуется установленный менеджер зависимостей `Poetry`. Перед стартом скопируйте файл конфигурации окружения `cp .env.example .env` и настройте параметры подключения к вашей локальной базе данных PostgreSQL.

* **Запуск сервера FastAPI локально (с флагом автоперезапуска `--reload`):**
  ```bash
  make run-local
  ```

## 📑 Описание API-контракта

Интерфейс спроектирован в строгом соответствии с REST-принципами и предназначен **только для чтения**. Вся структура данных валидируется через `Pydantic v2`.

### 1. Получить список доступных анкет
* **Маршрут:** `GET /api/v1/questionnaries/`
* **Логика:** Возвращает плоский список анкет (`Ident = 43005`), которые не удалены (`FlagDeleted = false`) и доступны для использования (`Tip2` равен `0` или `null`). Список отсортирован по названию по возрастанию.
* **Пример ответа (HTTP 200):**
  ```json
  [
    {
      "uid": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
      "name": "Анкета первичного осмотра терапевта"
    },
    {
      "uid": "7ba44f12-1217-4112-b3fc-2c963f66afb2",
      "name": "Опросник качества сна"
    }
  ]
  ```

### 2. Получить структуру конкретной анкеты
* **Маршрут:** `GET /api/v1/questionnaries/{questionnarie_uid}/`
* **Логика:** Собирает древовидную структуру анкеты:
  * Общий плоский список вариантов ответов (`Ident = 79000 + Cod анкеты`).
  * Вопросы (`Cod = 41`), отсортированные по полю `Count_1` по возрастанию.
  * Если у вопроса `Count_5 != 0`, он автоматически группируется в соответствующий блок (`Ident = 43010`).
  * Если `Count_5 == 0`, вопрос попадает в секцию `ungrouped_questions`.
* **Пример ответа (HTTP 200):**
  ```json
  {
    "uid": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
    "name": "Анкета первичного осмотра терапевта",
    "options": [
      { "uid": "a1b2c3d4-...", "value": 1, "text": "Да" },
      { "uid": "e5f6g7h8-...", "value": 2, "text": "Нет" }
    ],
    "question_groups": [
      {
        "uid": "99999f64-...",
        "name": "Общие симптомы",
        "questions": [
          {
            "uid": "11111f64-...",
            "short_text": "Жалобы",
            "full_text": "Имеются ли у вас жалобы на здоровье в данный момент?",
            "is_required": true,
            "order": 1
          }
        ]
      }
    ],
    "ungrouped_questions": [
      {
        "uid": "22222f64-...",
        "short_text": "Примечания",
        "full_text": "Дополнительные комментарии врача",
        "is_required": false,
        "order": 1
      }
    ]
  }
  ```
* **Коды ошибок:** 
  * `HTTP 404 Not Found` — если анкета удалена, недоступна или UUID не существует в системе.
  * `HTTP 422 Unprocessable Entity` — если передан некорректный формат UUID.

## 🧠 Принятые архитектурные решения и допущения

1. **Многослойная архитектура (Layered Architecture):**
   Приложение жестко разделено на слои для обеспечения масштабируемости и тестируемости:
   * `HTTP Слой (FastAPI Routers)` — обрабатывает запросы, отвечает за HTTP-статусы и валидацию входящих/исходящих данных через Pydantic. Лежит в папке **api**
   * `Инфраструктурный слой` — конфигурация асинхронного движка SQLAlchemy 2.0 и DI-генераторы сессий.  Лежит в папке **infrastructure/db**
   * `Слой данных (Repository)` — инкапсулирует в себе всю специфику построения SQL-запросов и сборку сложных структур в памяти. Реализует адаптеры для портов из доменного слоя. Лежит в папке **api/repositories**
   * `Прикладной (Use cases)` — содержит в себе логику и dto для передачи данных между слоями. Лежит в папке **application**
   * `Доменный (Domain)` — сущности с которыми ведется работа и порты-контракты (repo-s). Лежит в папке **domain**

   Каждый слой ничего не знает про высший слой, но использует в своем коде низший слой.

2. **Отсутствие Foreign Keys на уровне БД:**
   Поскольку таблица `reference_items` представляет собой полиморфный денормализованный справочник (в ней вперемешку лежат и анкеты, и группы, и варианты ответов), классические `ForeignKey` связи на уровне PostgreSQL отсутствуют. Связывание сущностей (например, `Question.count_5` -> `ReferenceItem.cod` при условии `Ident = 43010`) реализовано на прикладном уровне с использованием явных `JOIN`-запросов с алиасами моделей (`aliased`).

3. **Оптимизация производительности (Проблема N+1):**
   Для сборки дерева конкретной анкеты репозиторий **не выполняет** запросы в цикле. Вместо этого за фиксированные 3 запроса к БД (сама анкета ➡️ пачка вариантов ответов + пачка вопросов + пачка групп вопросов) вычитывается весь массив данных, а группировка в древовидную структуру эффективно выполняется силами Python в памяти перед отдачей клиенту.

4. **Изоляция CLI и процессов в Docker:**
   * Автоматическое создание схемы и наполнение базы вынесены из жизненного цикла (`lifespan`) FastAPI в отдельные CLI-скрипты.
   * Скрипт `/entrypoint` содержит механизм **Healthcheck**, который дожидается полной готовности PostgreSQL принимать соединения прежде, чем запустить процесс миграций и сидинга.
   * Команда запуска в контейнере реализована через Bash-инструкцию `exec`, что делает процесс веб-сервера основным процессом (**PID 1**), гарантируя корректную обработку сигналов `SIGTERM` и безопасную остановку контейнера (Graceful Shutdown).
